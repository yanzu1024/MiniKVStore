# MiniKV Store 项目理解与面试讲解

## 1. 一句话介绍

MiniKV Store 是一个纯 C++17 本地键值存储引擎，通过二进制追加日志持久化写操作，以哈希索引定位最新磁盘记录，并使用 LRU 缓存、TTL 后台清理和日志压缩改善读取与空间管理。

## 2. 主要对象关系

```text
main / CommandParser
          ↓
    KeyValueStore
      ├── unordered_map<string, RecordMetadata>
      ├── LruCache<string, string>
      ├── unique_ptr<AppendOnlyStore>
      └── cleanerThread
                    ↓
              binary AOF file
```

`KeyValueStore` 是业务入口，负责并发控制和各组件协作；`AppendOnlyStore` 只处理文件格式、读写、恢复与压缩；`CommandParser` 只负责把文本转换成结构化命令。

## 3. 为什么索引中不直接保存值

索引类型是：

```cpp
std::unordered_map<std::string, RecordMetadata>
```

其中 `RecordMetadata` 保存：

- 记录起始偏移量；
- 值在文件中的偏移量；
- 值长度；
- 绝对过期时间。

如果所有值本来就完整保存在内存字典中，再增加 LRU 会变成没有实际意义的重复缓存。当前设计只把索引和有限热点值放进内存，使缓存命中和磁盘未命中具有明确含义。

## 4. SET 的执行过程

```text
检查存储是否打开
  ↓
检查键和值长度、TTL
  ↓
获取 indexMutex 独占锁
  ↓
向 AOF 尾部追加 SET 记录并 flush
  ↓
更新 key → RecordMetadata
  ↓
将新值放入 LRU
  ↓
释放锁并更新统计
```

只有文件追加成功后才修改内存索引，避免出现“内存显示写入成功，但磁盘没有记录”的顺序错误。

## 5. GET 的执行过程

```text
通过 unordered_map 查找元数据
  ↓
检查绝对过期时间
  ↓
查询 LRU 缓存
  ├─ 命中：直接返回
  └─ 未命中：按照 valueOffset 从 AOF 读取
                         ↓
                    写入 LRU 并返回
```

GET 持有共享锁，因此多个读操作可以并发。写入和压缩需要独占锁。

## 6. LRU 为什么是 list + unordered_map

`std::list` 的节点移动和删除不会使其他节点迭代器失效，适合维护最近使用顺序：

- 表头：最近使用；
- 表尾：最久未使用。

但只使用 `list` 查找键需要 O(n)。因此再使用：

```cpp
unordered_map<Key, list迭代器>
```

将键映射到链表节点，平均 O(1) 找到并移动节点。容量满时删除链表尾部，同时从哈希表删除对应键。

## 7. 二进制序列化为什么不直接 write(struct)

C++ 结构体可能包含：

- 编译器插入的内存填充；
- 与平台相关的字节序；
- 不同编译器或编译选项造成的布局差异。

当前代码使用固定字段宽度，并显式写入每个小端序整数。这样文件格式由代码协议定义，而不是由当前机器的内存布局定义。

## 8. 启动恢复

恢复过程顺序扫描 AOF：

1. 读取固定长度头部；
2. 检查 magic、版本、操作类型和长度边界；
3. 读取键和值；
4. 重新计算校验值；
5. SET 更新索引，DEL 删除索引；
6. 已过期的 SET 会删除该键在之前记录中留下的旧状态。

索引最终保存每个键的最新有效记录。

## 9. 为什么截断尾部和校验失败处理不同

如果程序在写一条记录的过程中终止，文件末尾可能只剩部分头部或部分内容。恢复时可以确认最后一条记录不完整，因此把文件缩回最后一个完整记录的位置。

校验失败则可能表示中间数据被修改或损坏。程序不能确定“从哪里开始都可以安全删除”，所以返回 `CORRUPTION`，不静默破坏原文件。

## 10. TTL 机制

TTL 保存为绝对 Unix 毫秒时间戳，而不是“还剩多少秒”。这样程序重启后仍能判断是否过期。

项目同时使用：

- 惰性过期：GET 时检查；
- 主动清理：后台线程定期扫描索引。

即使后台线程还没来得及删除，GET 也绝不会返回已经过期的值。

## 11. 后台线程与 RAII

清理线程的循环通过 `condition_variable::wait_for()` 等待。关闭时：

1. 原子停止标志设为 `true`；
2. `notify_all()` 立即唤醒等待；
3. `join()` 等待线程退出；
4. 对象随后才开始销毁成员。

不能使用 `detach()`，否则线程可能在 `KeyValueStore` 已销毁后继续访问成员。

所有锁通过 `lock_guard`、`unique_lock` 和 `shared_lock` 管理。函数提前返回时，锁对象析构会自动释放锁，这就是 RAII。

## 12. unique_ptr 的真实用途

```cpp
std::unique_ptr<AppendOnlyStore> storage_;
```

表示一个 `KeyValueStore` 独占自己的存储后端。它不需要共享所有权，因此不用 `shared_ptr`。析构时 `unique_ptr` 自动释放后端，也为以后替换存储实现保留了清晰的所有权边界。

值类型成员如 `LruCache` 不需要动态分配，所以直接作为普通成员保存。

## 13. COMPACT 的执行过程

追加日志中会同时存在旧值、删除记录和过期记录。压缩过程：

1. 获取引擎独占锁；
2. 删除已过期索引；
3. 读取所有当前有效值；
4. 写入 `.compact.tmp` 临时文件；
5. 刷新并关闭临时文件；
6. 用临时文件替换原 AOF；
7. 根据新偏移量替换内存索引；
8. 清空旧 LRU 数据。

在临时文件完整写好前不动原文件，降低压缩失败破坏已有数据的风险。

## 14. Status 与 Result

预期错误不使用异常控制普通流程：

- `Status` 表示只有成功或失败、没有返回值的操作；
- `Result<T>` 同时保存 `Status` 和可选结果；
- `NOT_FOUND`、`INVALID_ARGUMENT`、`IO_ERROR`、`CORRUPTION` 和 `CLOSED` 可以区分。

异常只用于真正违反 `Result` 使用约定的情况，例如对失败结果强行调用 `value()`。

## 15. 测试覆盖

- LRU 命中、更新、淘汰和统计；
- 引号、转义、TTL 和错误命令；
- SET/更新/删除后的重启恢复；
- 压缩前后数据一致性；
- 不完整尾部自动截断；
- TTL 惰性检查与后台清理；
- 6 个线程并发 SET/GET；

项目支持 ASan/UBSan 和 ThreadSanitizer 构建。Sanitizer 通过不代表程序已经达到生产级，但能够发现普通测试不容易暴露的内存、未定义行为和数据竞争问题。

## 16. 高频面试问题

### 为什么不用 `std::map`？

当前索引不需要自动保持键有序，核心需求是按键快速定位，因此选择平均 O(1) 查找的 `unordered_map`。`KEYS` 输出时再对结果排序。

### 为什么写文件时还要锁索引？

SET 的文件记录和内存元数据必须作为一个顺序一致的操作完成。如果并发写同一个键，独占锁保证“最后成功追加的记录”与“最终索引”一致。

### 为什么文件还需要自己的 mutex？

`fstream` 的读写位置和状态标志属于共享可变状态。即使索引允许多个 GET 并发，也不能让多个线程同时修改同一个流的位置。

### `flush()` 是否保证断电不丢数据？

不能。`flush()` 把 C++ 流缓冲交给操作系统，但不等同于将数据强制落到物理介质。生产级持久化还需要设计 `fsync` 策略、批处理和崩溃一致性。

### 压缩期间能否继续写？

当前不能。压缩持有引擎独占锁，设计简单且容易验证。进一步优化可以使用快照、增量日志或后台合并，但会显著增加一致性复杂度。

### 性能瓶颈在哪里？

每次写入都会 flush，磁盘读由单个文件互斥锁串行化，压缩也会阻塞其他操作。这些是为了清晰性和正确性作出的第一版取舍。
